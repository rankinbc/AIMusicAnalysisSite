01

Page anatomy & layout

The page is a single vertical composition with a persistent right rail. From top to bottom:

  • Header bar — track identity, the mode switcher, and the Coach mascot entry point.
  • Visualizer stage — the dominant element; a host-driven canvas that can composite several visual stages.
  • Transport + waveform — play controls, scrubbable waveform with markers, time, volume, add-note.
  • Bottom module — a single window that toggles between the Rack (▦) and the Visuals console (☀), with a shared header holding the toggle, context presets, and the "controlled by" chip.
  • Right rail — stacked panels: Coach, People, Chat, Stats, Notes (composition varies by mode).
  • Tweaks panel — floating, host-provided; layout/mode controls for the prototype.
Canvas is ~1640px wide; the visualizer and rack are the two largest regions. Right rail is fixed-width.
02

Track identity & transport

Track identity

Title, artist line, genre, and (planned) version label in the header.

  • Title (e.g. "Aurora — Final Mix"), with artist sub-line: user-icon avatar + "by Mae Karlsson · @maek".
  • Genre tag below the title.
Add: a version label (v1/v2/v3) that ties into the versions/presets model — see §6.

Playback transport

  • Play/pause (large primary), skip back/forward, current/total time.
  • Volume control with live readout.
  • Add note @ timestamp button anchored to the playhead.
Host-driven in Room (everyone synced to host clock); local in Work/View.

Waveform scrubber

  • Scrubbable waveform with a live playhead.
  • Markers overlaid: note markers (click to seek), reaction markers.
Persistence: playback position stored in localStorage; re-read on load.
03

Visualizer stage

A host-driven canvas that renders one or more stages at once. Stages are multi-select and composite live on a single canvas.

Stages (composable)

Toggle any combination — they layer (e.g. EQ spectrum + radial pulse + colored smoke).

  • EQ — spectrum bars with frequency + dB axis measurements.
  • Devices — the active rack chain as a looping, side-scrolling marquee of color-coded cards.
  • Radial, Orbit, Bloom — geometric reactive forms.
  • Smoke — colored volumetric haze.
  • Spectrogram — scrolling frequency/time heat.
  • Light — the laser rig (see §4).
  • Listeners — presence-driven visual.
  • Track — track info card.
State: stages = array of active stage ids. toggleStage(id) adds/removes.

Coach announcement banner

When the Coach broadcasts, a banner appears at the top of the visualization with a stage-scoped flash.

Flash is scoped to the stage element only (not the whole page).
04

Visuals console

RoomView*

The bottom module in ☀ mode: a hardware lighting console skin — engraved header, status LEDs, screws, and labeled module bays. Header matches the rack (cyan dot + "VISUALS CONSOLE" + live meta + actions). Bays:

Primary actions

  • Sync all to music — master toggle that arms every per-module sync at once.
  • Color sync · theme — 3 color swatches that map to spectrum / lasers / background, plus a Sync apply button.

Stage select

Backlit cell buttons, one per stage, with on/off LED; combine multiple. Mirrors the canvas stages state.

Auto program (directors)

Preset "programs" that set modules automatically: Manual, Chill, Club, Hype, Pulse, Drift, Strobe, Minimal.

State: director id. Selecting one writes a bundle of viz settings ("sets modules"). Manual = hands-on.

Auto-react to music

  • Toggle + sensitivity slider. Loud/intense parts add layers and push the lasers; quiet parts strip back to a calm visual.
State: viz.autoReact (bool) + sensitivity (0–100).

Primary color

(Formerly "Spectrum color.") Curated color swatches + a spectrum-hue slider + a per-module SYNC toggle.

State: viz.barColor / viz.specHue, viz.autoColor (sync).

Laser rig

  • Effect (e.g. beat), Pattern (e.g. fan), Intensity slider.
  • Roam light source — apex jumps to a new position every couple seconds then holds (moving-head feel).
  • Color / mono color, and a SYNC toggle.
State: viz.laser* (effect, pattern, intensity, color/hue, mono, roam), viz.laserSync.

Background

  • Flash background toggle + flash rate slider (0.5–8 Hz) + color swatches — strobes the whole stage.
  • Cycle toggle (auto-rotate background color) and a SYNC toggle.
State: viz.bg* (color/hue, flash, flashRate, cycle/auto), viz.bgSync.

FX · moments

Sync fireworks to drops — fires a burst FX on detected drops.

State: viz.dropFx (bool).

Per-module sync & Randomize

  • Laser, Primary color, Background and FX each carry their own SYNC toggle binding them to the music; "Sync all" arms them together.
  • Randomize — shuffles the console into a new look in one tap.
05

The Rack

WorkRoom

The audio processing chain — the heart of Work mode. Built from 14 modules defined in the rack manifest (EQ, Compressor, M/S Width, Limiter, Output Trim, and creative/utility modules).

Module anatomy

  • Enable toggle per module; disabled modules can collapse via "Show inactive".
  • Params rendered from the manifest: knobs, bipolar knobs, sliders, toggles, segmented controls, selects — each with range/default/units.
  • GR meter (gain reduction) and modulation indicators where relevant.
Source of truth: rackManifest.ts — module ids, param specs, ranges, defaults. State: rs.mod[id].{enabled, params…}.

Layouts

  • Inline — rich horizontal chain, controls exposed, drag-reorder.
  • Console — denser channel-strip view.
  • Studio — expandable detailed view.
State: ia (inline | console | studio), set via Tweaks.

Rack chrome

  • ● INSERT RACK label + live active count + signal-flow readout.
  • ⌁ Bindings — modulation matrix (params bound to sources).
  • A/B Bypass — compare processed vs. bypassed.
  • ↺ Reset — restore defaults.
  • Show inactive — collapse/expand disabled modules.

Reorder & A/B

  • Drag to reorder modules in the chain.
  • A/B compare between two saved states.
06

Presets & versions

WorkViewRoom

The most tangled area, and the reason for this reference. There are several distinct "preset"-like concepts that need clear separation in the data model:

Track versions

A track can have multiple versions (v1 / v2 / v3 …). The header version label selects which is active.

Open: is a version an immutable snapshot of audio + rack, or just a label? See §19.

Rack presets — associated with a version

A saved rack state (all module enables + params + order). Per your note, a rack preset is saved against a specific version of the track.

State today: rs.presets[] with recall/save. Needs: a versionId on each preset, and UI to scope the preset list to the active version.

Visual presets

A saved snapshot of the whole visuals console (stages + viz settings). Context-aware presets control in the shared header saves/recalls these when in ☀ mode.

State: vizPresets[]; saveVizPreset / recallVizPreset.

Suggested presets (from reviewers)

In View, a reviewer can attach a rack preset to a comment as a suggestion; the author can audition and accept it.

Open: accept = full replace vs. cherry-pick modules. Relationship to versions. See §19.

Director presets (built-in)

The Auto-Program programs (Chill/Club/Hype…) are read-only built-in visual presets — distinct from user-saved visual presets.

Suggested data model

// distinct concepts, related by ids
Track       { id, title, artist, genre, versions[] }
Version     { id, label:"v3", audioRef, createdAt }
RackPreset  { id, name, versionId, author, chain[], createdAt }
VizPreset   { id, name, author, stages[], viz{} }
Suggestion  { id, versionId, fromUser, rackPreset, commentId, status }
Key relationship: RackPreset.versionId scopes presets to a version; Suggestion wraps a RackPreset proposed by a non-author.

Coach & Plan

WorkView*

Coach mascot & chat

  • Animated mascot (domed helmet, neon-green rim, antenna, swept fins, side pods, violet visor, EQ-bar mouth).
  • Chat interface — ask about the mix; the Coach replies with analysis.
  • Apply suggestion — inline button on any message proposing a concrete fix; applies it to the rack.

Coach announcements

The Coach can broadcast to a Room — surfaces as the stage banner (§3) for everyone.

Plan

A ranked list of suggested fixes ("determine improvements"), each applyable.

Presence & people

Room

Listener presence

  • Listener avatars (color hue per user, anon supported) with a live status emoji.
  • Status sentiment range, color-coded: Positive 👍🔥🤯😲🙌💜 (green) · Neutral 👀🤔😐 (muted) · Negative 👎😴🥱😬 (red).
  • HOST badge on the session host.
  • Presence pops on the stage — avatar + emoji + @handle appear transiently.
State: ROOM_LISTENERS[] (handle, hue, anon, status); myStatus for the local user.

Comments & feedback

View

Timestamped & general comments

  • Timestamped — anchored to a point on the waveform ("vocal too low @ 1:24").
  • General — track-level notes not tied to a moment.
  • Author can resolve / pin / hide; visibility to other viewers is uploader-controlled.
State: comments[] {id, t|null, author, body, status, suggestionId?}.

Attached suggestions

A comment can carry a suggested rack preset (§6) the author can audition.

Control granting

Room

Independent rack / visuals handoff

  • The host can grant rack control and visuals control to listeners separately (e.g. @forge → rack, @vela → visuals).
  • A "controlled by" chip in the bottom module shows the active controller per view (rack · @forge / visuals · @vela).
State: rackController, visualController (handles); onGrant(view, handle).
15

Modes

The page resolves into three modes — see the Three Modes spec for the full treatment. In short:

  • Work  solo, private — rack + Coach + metering; social hidden.
  • View  async review — comments, suggested presets, bookmarking.
  • Room  live session — presence, chat, reactions, full visuals, control handoff.
The mode switcher replaces today's SOLO ⇄ ROOM control. Per-feature mode tags appear throughout this doc.

Permissions & sharing

Set by the uploader; these gates decide which features render in View/Room:

  • Visibility — Private / Unlisted / Public.
  • Comments — on/off + who may comment.
  • Suggested presets — allowed or not.
  • Bookmarking — allowed or not.
  • Live sessions — who can host / join a Room.

18

State & persistence

What the page keeps, and where, for implementation:

  • Playback position — localStorage, re-read on load.
  • Rack state — rs.mod[id] (enabled + params + order); presets in rs.presets[].
  • Visuals state — stages[] + viz{} object; vizPresets[].
  • Social — feed[], comments[], ROOM_LISTENERS[], controllers — host-synced in Room, persisted on the track in View.
  • Tweaks — persisted by the host protocol.
Rule of thumb: Work state is local & private; View state persists on the track; Room state is host-driven & ephemeral (with a recap snapshot).
19

To define

Decisions before implementation

  1. Version model — is a Version an immutable audio+rack snapshot, or a label over a mutable rack?
  2. Preset ↔ version binding — do presets always belong to one version, or can they be promoted/copied across versions?
  3. Suggestion merge — accept = full rack replace vs. cherry-pick modules/params.
  4. Anon participation — can anonymous viewers comment / suggest / bookmark?
  5. Bookmark signal — private save vs. visible to author.
  6. Room recap → View — automatic or opt-in; which moments convert to comments.
  7. Coach in View — author-only or available to reviewers.
  8. Notifications — where the author sees new comments/suggestions.
